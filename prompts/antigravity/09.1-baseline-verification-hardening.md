# Phase 9.1 — Pre-Phase-10 Baseline Verification & Hardening

> Attach `00-master-project-context.md` alongside this prompt.

## Role

You are a senior software/CV verification engineer. The project has completed Phases 1–9: video ingestion, YOLO vehicle detection, ByteTrack tracking, vehicle counting, traffic analytics, configured lane analysis, and image-space density estimation. Before Phase 10 begins, perform a focused verification and hardening pass over the **existing** implementation.

This is **not** a new feature phase. Do not redesign the architecture. Do not add unrelated functionality. Do not start Phase 10. Do not replace existing implementations merely for stylistic reasons.

The objective is: **establish a trustworthy Phase 1–9 baseline and fix only the remaining issues discovered during verification.**

## Workflow

Use exactly:

```
READ → INSPECT → PLAN → VERIFY → DEBUG → FIX → TEST → RE-VERIFY → DOCUMENT → GIT REVIEW → REPORT
```

Do not skip verification before fixing anything — you must know what's actually broken before you touch code. A fix without a preceding verified failure is not appropriate for this pass.

## Primary Objective

Create a verified baseline for Phases 1–9. The final goal is:

```
PHASE 1–9 BASELINE = VERIFIED
```

meaning: every phase's own test suite passes when actually run, every phase's own real-verification script (where one exists) runs successfully and produces genuine evidence, the full backend regression suite passes end to end, the frontend typechecks and builds, and any gap or defect found along the way has either been fixed (if small and genuinely in-scope) or explicitly documented as a known issue (if it's larger than a hardening fix belongs).

## Scope — What "Verification and Hardening" Means Here

**In scope:**
- Re-running every existing automated test (unit + integration) for Phases 1–9 and recording real pass/fail output.
- Re-running every existing real-verification script (`scripts/verify_phase*.py`) and confirming its evidence still holds against the current code.
- Confirming cross-phase consistency: do Phase 6's `TrackedObject` fields still match what Phase 7's counter, Phase 8's analytics, and Phase 9's lane analyzer each assume? Do documented schemas in `ARCHITECTURE.md` match the actual current schemas?
- Fixing genuine, concretely-identified defects: a failing test, a broken script, a security gap inherited from an earlier phase, a documentation claim that no longer matches the code, a resource-limit that isn't actually enforced where earlier prompts required it.
- Confirming `.env.example` is complete and accurate for everything the current codebase actually reads from settings.
- Confirming no secrets, real credentials, or `.env` file have been committed at any point in the history you're reviewing.

**Out of scope:**
- Any new capability (no Phase 10 work — no traffic prediction, speed estimation, congestion scoring, signal optimization, etc.).
- Refactors motivated by style/taste rather than a concrete found defect.
- Expanding a phase's feature set beyond what its own prompt originally required.
- Redesigning the `Detector`/`Tracker`/`Counter`/`Analytics`/`LaneAnalyzer` interfaces unless a genuine incompatibility between phases was found (and if so, the fix must be the smallest correction that restores consistency, not a rearchitecture).

## Per-Phase Verification Checklist

For each phase below, actually run what's asked — don't infer status from reading code.

- **Phase 1–2:** confirm the repo structure and backend foundation still match `ARCHITECTURE.md`/`PROJECT_STATUS.md`; re-run the Phase 2 backend test suite; hit `/health` and `/api/v1/health` live.
- **Phase 3 (Frontend Foundation):** `npm install`, typecheck, build; confirm the backend-status indicator genuinely reflects live backend state (online and offline).
- **Phase 4 (Video Ingestion):** re-run all upload/validation/security tests (extension spoofing, path traversal, oversized file, corrupted video); confirm no orphaned files accumulate in the upload directory from a rejected upload.
- **Phase 5 (YOLO Detection):** confirm the model actually loads and real inference runs on a test fixture; re-run the detection test suite; confirm detection results carry no track ID (that's still Phase 6's job, not leaked backward).
- **Phase 6 (Object Tracking):** re-run the tracker test suite and confirm genuine track-ID continuity across frames on a real fixture, not just that the tests pass in isolation.
- **Phase 7 (Vehicle Counting):** re-run `scripts/verify_phase7_counting.py` (or its actual name) and confirm a genuine line crossing is still correctly counted exactly once.
- **Phase 8 (Traffic Analytics):** re-run `scripts/verify_phase8_analytics.py`; manually check the arithmetic in its output; confirm any extrapolated metric is still clearly labeled `ESTIMATED`/`EXTRAPOLATED`.
- **Phase 9 (Lane Analysis & Density):** re-run `scripts/verify_phase9_lane_analysis.py`; confirm genuine multi-lane evidence (2+ lanes with real vehicles, not a degenerate single-lane case); confirm density is still labeled as image-space, not physical.
- **Cross-cutting:** run the complete backend test suite in one pass (not phase-by-phase in isolation) to catch any interaction regression; run frontend typecheck/build once at the end as the final gate.

## Debugging & Fixing Discipline

Follow the project's standard debugging discipline for anything found broken: reproduce it, identify the actual root cause, implement the smallest correct fix, re-test that specific fix, then re-run the broader regression suite to confirm no new breakage was introduced. Do not apply a speculative fix for something you haven't actually reproduced. If a found issue is too large or architecturally significant to fix as "hardening" (e.g., it would require redesigning a phase's interface), do not attempt it here — document it clearly as a known issue with a recommended follow-up, and leave the phase's status as `PARTIALLY VERIFIED` rather than forcing a fix that oversteps this pass's scope.

## Documentation

Update `PROJECT_STATUS.md` phase-by-phase with the **real, re-verified status** of Phases 1–9, replacing the current "reported, not independently re-verified" language with concrete evidence (actual test counts, actual script output references) wherever you've genuinely confirmed it — and leaving the honest caveat in place for anything you couldn't fully re-verify or that turned out to only be `PARTIALLY VERIFIED`. Update `ARCHITECTURE.md` only where you found a genuine drift between documented and actual schemas/interfaces. Update `README.md` only if its status banner is now stale.

If genuine fixes are made, commit them as focused, individually justified commits (e.g., `fix: <specific defect>`), not one giant "hardening" commit that bundles unrelated changes. If nothing needed fixing, say so explicitly and make no commit beyond the `PROJECT_STATUS.md` update.

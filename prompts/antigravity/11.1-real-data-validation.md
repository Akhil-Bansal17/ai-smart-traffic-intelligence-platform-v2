# 11.1 — Real-Data Validation & Hardening

> Attach `00-master-project-context.md` alongside this prompt.

## Role

You are a senior AI/ML verification engineer. Phase 11 built a functionally strong prediction system, but its own verification found **zero real observations** in PostgreSQL and fell back to 120 synthetic fixture rows to demonstrate the pipeline. This phase is **not a new prediction feature** — it is a real-data validation and hardening pass to establish whether the existing Phase 11 system can genuinely train and forecast on real traffic observations produced by the platform's own Phase 4–10 pipeline.

## Objective

```
Real Video → YOLO → Tracking → Counting → Traffic Analytics → PostgreSQL
  → Real Prediction Dataset → Feature Engineering → Chronological Train/Test
  → ML Model → Real-Data Forecast → Persistence → API → Frontend
```

Prove — or honestly disprove — that the prediction layer consumes genuine persisted traffic observations when sufficient real data exists. Do not solve this by lowering the minimum threshold, misclassifying synthetic data as real, fabricating historical records, or fabricating metrics.

## Scope — Five Objectives

1. Verify the real-data pipeline from persisted Phase 10 records into Phase 11.
2. Generate sufficient genuine observations using the existing CV pipeline where needed (never fake rows).
3. Verify the ML pipeline correctly distinguishes real data from synthetic fixtures.
4. Validate training/evaluation/forecasting using genuinely persisted traffic data.
5. Harden documentation, verification, and regression gates — no unrelated features.

## Real vs. Synthetic — The Central Distinction

Synthetic fixtures for development must remain available, but Phase 11.1 must make the distinction unmistakable everywhere:

- **Real:** data produced by actual traffic-video processing, persisted through the genuine Phase 4–10 pipeline.
- **Synthetic:** artificial development fixtures generated intentionally for testing/fallback.

Never allowed: synthetic rows labeled real; a synthetic prediction run labeled `real_observations`; fabricated historical traffic counts; fake confidence values; fake evaluation metrics; fake timestamps pretending to represent real traffic; hardcoded real-data verification output.

## Real Data Generation Strategy

First determine *why* the database currently has zero usable real observations. Inspect: how `AnalysisSession` gets created, how `TrafficMetricsRecord` gets persisted, whether completed analysis sessions actually produce traffic metrics, whether existing uploaded/verification videos are available, whether a genuine sequence of analysis runs can be produced from them, whether each run yields one or multiple usable observations, whether timestamps support chronological prediction, and whether the dataset extractor correctly queries only valid completed real records. **Never create fake rows to satisfy the threshold.** If legitimate test/verification videos exist, you may process them through the real Phase 4–10 pipeline to produce genuinely real (if verification-derived) observations — keep them clearly identifiable as such. If more videos are genuinely needed and can't be produced automatically, document that limitation rather than fabricating data.

## Data Provenance Requirement

Determine whether the current schema can reliably distinguish real observations, synthetic fixtures, other dev/test records, and prediction outputs. If it can't, implement the smallest necessary hardening (e.g., a source/provenance field) — don't redesign the database. Any schema change: create an Alembic migration, preserve existing data, define safe defaults, document semantics, test upgrade/downgrade/re-upgrade, and confirm Phase 1–10 behavior stays intact. Never silently reinterpret old synthetic data as real.

## Real Observation Quality Requirements

Before training on real data, inspect actual rows for: completed status, valid timestamps, non-negative volume, valid observation duration/flow metrics/class and direction distributions, no impossible values, no duplicates, chronological order, no future timestamps relative to the training cutoff, no obvious leakage, sufficient temporal coverage. Don't just count rows — 20 duplicated or near-identical records is not a trustworthy dataset. Report: usable count, rejected count and reasons, earliest/latest timestamp, temporal span, distinct session/video counts, volume range and central tendency, missing-value count, duplicate count.

## Minimum Data Threshold

The existing threshold is `MIN_TRAINING_SAMPLES = 20`. Do not lower it just to make training succeed. Determine whether 20 is actually sufficient for the existing 11-feature model and chronological split — if it's technically too small for meaningful evaluation, improve the readiness logic rather than pretending otherwise. Distinguish: structurally trainable, minimally evaluable, and reasonably useful for forecasting. If the architecture can't make a scientifically meaningful claim with available real data, say so — prefer "real data insufficient for trustworthy forecasting" over a misleading prediction.

## Time-Series Leakage Verification (critical)

Verify explicitly: lag features use only earlier observations; rolling windows use only historical values; target values never leak into current-step features; chronological ordering happens before feature construction where required; the train/test split is chronological; test observations never influence training features; recursive future predictions never use future ground truth; residual uncertainty is calculated only from valid historical residuals. **Don't merely assert "no leakage" — create a verification case where future values are deliberately very different from past values, and prove that changing future values does not change features generated for earlier timestamps.**

## Real-Data Model Evaluation

When sufficient real observations exist, train the existing models on real data and evaluate both the selected model and the naive-persistence baseline using the existing chronological approach (unless inspection proves it's wrong). Report: training/test sample counts, model type, MAE, RMSE, R² (when statistically meaningful), baseline MAE/RMSE, improvement or degradation relative to baseline, training and inference duration. Never pick a model because it produces the prettiest numbers — if the naive baseline wins, report that honestly.

## Real-Data Forecast Verification

Generate multi-step predictions from a model trained on real observations and prove the output is genuinely dynamic — e.g., a low-input vs. high-input perturbation test showing the prediction responds accordingly (only if that relationship is actually implied by the trained model; don't require monotonicity that isn't real). Never hardcode expected numbers. Verify: horizon, predicted volume, lower/upper bounds, non-negative predictions where domain-required, correct interval ordering, finite values (no NaN/Inf), the uncertainty-interval calculation, and recursive-forecasting behavior.

## Uncertainty Hardening

Verify the empirical residual uncertainty implementation: residuals come from a genuinely valid held-out/evaluation source; uncertainty isn't fabricated; intervals behave logically if the implementation claims expansion; `lower ≤ prediction ≤ upper`; lower bound isn't negative where domain constraints require clipping; insufficient residual history produces an honest fallback/unavailable state rather than a guess. Use accurate terminology — **"empirical prediction interval," not an unsupported "confidence interval" claim** — unless actual statistical calibration is established.

## Prediction Data Provenance

Every persisted `PredictionRun` must clearly identify its data source — at minimum distinguishing `real_observations` from `synthetic_fixture`. Verify this thoroughly if it already exists in the schema; implement the smallest safe addition if it doesn't. The frontend must surface this plainly (e.g., "Real traffic observations," "Synthetic development fixture," "Real-data forecasting unavailable — insufficient historical observations"). Never display a synthetic prediction in a way that could be mistaken for a production forecast.

## Readiness API Hardening

Inspect `GET /api/v1/predictions/readiness`. It must distinguish at minimum: real data sufficient; real data insufficient; no real observations; invalid real observations; synthetic fixture available for development — not one collapsed generic state. It should expose enough for the frontend to explain *why* real forecasting is or isn't available.

## Training API Behavior

Inspect `POST /api/v1/predictions/train`. If sufficient real data exists and real-data training is requested, it trains on real observations. If real data is insufficient, it must **never silently fall back to synthetic data while claiming a real result** — it must return a truthful insufficient-data response, require an explicit development/synthetic mode, or use another clearly documented mechanism, with the distinction visible in both the API response and the persisted `PredictionRun`.

## Synthetic Fixture Behavior

Synthetic fixtures may remain for development/testing but generation must be explicit and clearly labeled (e.g., development/test only). Verify `POST /api/v1/predictions/fixtures/generate` cannot cause normal real-data training to accidentally consume fixture rows as if real — inspect the actual database queries/filtering to confirm real-data extraction excludes synthetic records.

## Database Consistency

Verify the full chain `Video → AnalysisSession → TrafficMetricsRecord → DatasetExtractor → FeatureEngineer → TrafficPredictor → PredictionRun → PredictionItem`, including foreign keys and relationships. Confirm deleting a source analysis/video doesn't silently orphan prediction metadata. Don't alter existing cascade semantics without understanding current Phase 10 behavior; if cleanup behavior needs a change, test it explicitly.

## Real-Data End-to-End Verification Script

Create or update `scripts/verify_phase11_real_data.py` — a genuine verification tool connected to the actual configured database, with **no fabricated success output**. Roughly:

1. Verify database schema. 2. Count/inspect genuine real observations. 3. Determine readiness. 4. If insufficient, explain exactly why. 5. If legitimate traffic videos are available, process them through the actual verified CV pipeline where practical, persist the results, and re-query. 6. Recalculate the real-observation count. 7. Extract only genuine real observations. 8. Build the chronological feature matrix. 9. Verify no future leakage. 10. Train the selected model on real observations. 11. Evaluate against naive persistence. 12. Generate a multi-step real-data forecast. 13. Verify uncertainty intervals. 14. Persist the `PredictionRun`. 15. Open a fresh DB session and verify persistence. 16. Verify the REST API returns the real-data prediction. 17. Verify provenance says `real_observations`. 18. Verify synthetic fixture records are excluded from the real dataset. 19. Print timing/resource measurements. 20. Print a final evidence-based status.

## Verification Outcomes (all are legitimate — pick the one the evidence supports)

- **A — Real data ready + real forecast verified:** the ideal outcome.
- **B — Real data exists but insufficient:** report "real-data forecasting not yet verified." Do not fabricate.
- **C — Real pipeline exists but current fixtures can't produce enough observations:** report "blocked by insufficient real observations" with the exact reason.
- **D — A genuine defect prevents real-data extraction/training:** identify the root cause, fix it only if within this phase's scope, then re-run verification.

**Never make the script exit successfully just because the synthetic fallback works.**

## Primary Objective

Establish the exact provenance of every observation used by Phase 11's real-data validation. Trace the complete chain for each of the 34 observations:

```
PredictionRun → traffic_metrics → analysis_session → video → stored video/source → actual origin of the video
```

For each observation, determine: which video and analysis session produced it; whether that session used the genuine Phase 4–10 pipeline; what video file was actually processed and where it originated; whether it's genuine real-world traffic footage, an OpenCV-generated or other fixture-generator video, a test video created by a verification script, a manually inserted row, or a copied/replayed synthetic dataset; whether any synthetic generator participated anywhere in the chain; and whether the current `data_source` classification is actually truthful.

## Definition of "Real" (non-negotiable)

**A "real observation" means an observation ultimately derived from genuine recorded real-world traffic footage.** The following are explicitly *not* real-world traffic observations: OpenCV-generated traffic videos, moving-rectangle/car/bus fixtures, synthetic videos, test videos generated by a verification script, manually inserted `traffic_metrics` rows, synthetic ML fixtures, hardcoded traffic values, fabricated timestamps, or copied/replayed synthetic datasets.

**Critical distinction:** a synthetic video processed through the real YOLO → ByteTrack → Counting → Analytics pipeline is a **real pipeline test** — it proves the CV/ML machinery works — but it is **not a real-world traffic observation**. Synthetic video → real CV pipeline → PostgreSQL must still be classified as synthetic/test-derived data for ML-provenance purposes, no matter how "real" the processing steps were.

## Provenance Audit

Produce a complete audit, for every relevant video/session, based on actual database records and actual files — not inference from filenames alone when stronger evidence (the actual video content, its creation script, its file metadata) is available. Report per record: video ID, original filename, stored source, video metadata, source classification, analysis-session ID, analysis type, `traffic_metrics` IDs, observation timestamps, `data_source` classification, and whether synthetic generation was involved anywhere in the chain. A filename like "synthetic," "fixture," "test," "generated," or "verification" is useful supporting evidence, not sufficient evidence on its own — trace the actual generation/creation path where possible.

## Database Chain Verification

Verify `videos → analysis_sessions → traffic_metrics → prediction_runs`: correct foreign keys, correct session/video association, no orphan observations, no duplicated observation accidentally counted as an independent sample, genuine (not fabricated) timestamps and observation durations, traffic volumes actually sourced from analytics output, dataset extraction selecting exactly the intended records, and no path by which a synthetic fixture row can silently appear in the real dataset. If the current schema lacks sufficient provenance information, make the **smallest necessary** schema/application change — do not redesign the database. Any migration goes through Alembic.

## `data_source` Semantics

Audit what `data_source = "real_observations"` and `"synthetic_fixture"` actually mean in the implementation today. The system must be able to distinguish, without ambiguity: real-world observations vs. synthetic/test-pipeline observations (synthetic video through the real pipeline) vs. synthetic ML fixtures (never touched the CV pipeline at all). If the current two-value scheme can't represent this distinction reliably, make the smallest safe correction — potentially a third category. Never silently relabel synthetic observations as real, never delete legitimate test data just to make statistics look cleaner, and never fabricate a real observation.

## DatasetExtractor Audit

Inspect `DatasetExtractor.extract_from_db()` (or its actual current method name/location) and verify exactly which rows it selects. Confirm: real-data extraction excludes synthetic ML fixtures; synthetic fixtures are explicitly labeled as such; test/synthetic CV observations are never misclassified as genuine real-world traffic; no fallback path silently converts synthetic data into `real_observations`; the minimum training threshold stays at 20 unless you find strong, stated evidence it's wrong; the threshold is never lowered merely to make the system report readiness; insufficient real data remains an honest not-ready state. **Explicitly prohibited pattern:** real data insufficient → generate synthetic data → label as real → train → report a "real" forecast.

## Real Traffic Source Verification

If genuine real-world traffic videos already exist in the repository/environment, use them through the legitimate Phase 4–10 pipeline — never bypass it. Preferred chain: real traffic video → Phase 4 upload/registration → `VideoSource` → YOLO → ByteTrack → line-crossing counter → traffic-metrics engine → `AnalysisPersistenceService` → PostgreSQL → `DatasetExtractor` → `TrafficFeatureEngineer` → `TrafficPredictor`. If enough genuine real observations result, perform real-data forecasting validation. If genuine footage exists but observations are too few, report that honestly. **If no genuine traffic footage exists at all, do not manufacture it** — the correct result is "real-world traffic data unavailable/insufficient."

## Observation Quality Audit

For genuine real-world observations (if any are confirmed), inspect: timestamps and their temporal ordering, duplicate timestamps/observations, observation duration, frame count, fps, video duration, traffic volume, flow rate, inbound/outbound counts, class distribution, density, temporal spacing between observations, camera/geographic consistency if available, and whether multiple "observations" are actually just repeated analysis of the same short video. **10 analysis sessions do not automatically mean 10 independent traffic periods. 34 rows do not automatically mean 34 independent observations.** Determine whether the observations represent meaningful temporal variation, and report: earliest/latest timestamp, temporal span, unique-video count, unique-session count, observations per video, median observation interval, and any detectable duplicate/near-duplicate observations.

## Temporal Coverage

Assess whether the dataset has meaningful temporal diversity: different times of day, different traffic conditions, different dates, sufficient chronological spacing — or whether everything came from one short fixture/video played through the pipeline multiple times. Do not claim strong forecasting generalization if all observations span only a few seconds or minutes. If coverage is weak, document exactly that: "Pipeline validated, but real-world forecasting generalization remains limited by temporal coverage."

## Future-Leakage Verification (retain and strengthen Phase 11.1's test)

Use genuine real observations if available. For an observation at time `t_k`: modify all observations where `t > t_k` to an extreme value (e.g., 9999), recompute features, and confirm feature values at `t_k` are unchanged. Also manually inspect the implementation for: no future rolling windows, no centered rolling statistics, no target leakage, no test-set information leaking into feature scaling, no random shuffling of temporally ordered data, no future timestamps used as predictors. Report actual numerical evidence from the perturbation test, not just an assertion that it passed.

## Real-Data Model Evaluation

If ≥20 legitimate real-world observations are confirmed, train/evaluate using **only** genuine real-world observations: chronological split, explicit train/test counts, model name/configuration, MAE, RMSE, R² where meaningful, naive-persistence baseline, and the comparison between them. Never present synthetic metrics as real-world metrics. If there are fewer than 20 legitimate real-world observations, **do not lower the threshold to produce a model anyway** — report the real count, the threshold, and `readiness = false`, and classify real-data forecasting as insufficient.

## Synthetic Data Handling

Synthetic data remains valuable for unit tests, integration tests, ML pipeline development, regression verification, and deterministic demonstrations — keep it, but label it explicitly everywhere. The system/UI/report must distinguish "real-world traffic data" from "synthetic development fixture" from "test/synthetic CV-pipeline observation," never mixing them silently. Synthetic data may demonstrate the ML pipeline works; it must never be presented as evidence of real-world forecasting accuracy.

## `PredictionRun` Provenance

Inspect `PredictionRun.data_source` and verify it correctly describes the dataset actually used for that specific run — real-world data → `real_observations`; synthetic ML fixture → `synthetic_fixture`. If a more precise category is genuinely needed for synthetic-CV-pipeline observations, introduce it only if truly necessary, with the smallest possible change. A `PredictionRun` trained on synthetic/test observations must never claim `real_observations` just because those rows happened to pass through YOLO/ByteTrack/analytics on their way to the database.

## Training API Safety

Inspect `POST /api/v1/predictions/train`. Verify: insufficient real data never silently falls back to synthetic while claiming a real result; the requested data source is actually respected; the returned provenance matches the actual training data used; the persisted `PredictionRun`'s provenance matches it too; error/readiness states are honest; synthetic training is explicit, never implicit. Make the smallest safe correction if any of this is currently wrong.

## Readiness API

Inspect `GET /api/v1/predictions/readiness`. It must clearly answer: how many genuine real-world observations exist, the required threshold, whether real-data training is actually ready, why or why not, and whether currently-available observations are synthetic/test-derived. The frontend must never display "ready for real forecasting" when the underlying data is synthetic.

## Frontend Provenance

Inspect `frontend/src/pages/PredictionsPage.tsx`. The UI must distinguish real data, synthetic data, and insufficient data, and show provenance honestly — e.g., "Real-world traffic observations: 34" (or 0), and separately, "Synthetic development observations: 120." If real data is insufficient, show an honest unavailable/not-ready state. Never hide that a prediction was trained on synthetic data. Make only the minimal correction needed for truthful provenance — don't redesign the dashboard.

## Real-Data Verification Script

Inspect and, if necessary, minimally correct `scripts/verify_phase11_real_data.py`. It must provide actual evidence for: database connectivity; the provenance audit; a count of genuine real-world observations; a count of synthetic/test-derived observations; `DatasetExtractor` behavior; readiness; confirmation that no synthetic fallback is mislabeled as real; timestamp ordering; temporal coverage; the feature matrix; the future-perturbation leakage experiment; and — only if enough genuine real data exists — chronological training, held-out evaluation, baseline comparison, dynamic prediction, and persistence. Also verify REST API provenance and frontend state where practical, and report the exact final classification (see below). **The script must never manufacture genuine real-world data.**

## Required Final Classification (exactly one of these four)

- **Outcome A — Real data verified:** genuine real-world traffic videos confirmed, sufficient genuine observations, provenance verified, synthetic data excluded from the real dataset, chronological evaluation completed, no leakage, predictions genuinely trained from real observations, persistence/API/frontend provenance all verified, regression passes → **Phase 11 real-data validation = VERIFIED.**
- **Outcome B — Real data exists but insufficient:** genuine footage confirmed, observations exist, but below the threshold or with insufficient temporal coverage → **Phase 11 implementation = VERIFIED; real-data forecasting validation = PARTIALLY VERIFIED.** Do not lower the threshold to force Outcome A instead.
- **Outcome C — Only synthetic/test traffic data available:** videos were generated/test fixtures, genuinely processed by the real CV pipeline, but the source footage is not real-world traffic → **CV-to-ML pipeline validation = VERIFIED; real-world traffic forecasting = NOT YET VERIFIED; Phase 11 remains PARTIALLY VERIFIED.**
- **Outcome D — Provenance or data-integrity defect:** observations mislabeled, synthetic rows misclassified as real, a broken foreign-key chain, a silent fallback, fabricated/hardcoded data, inconsistent provenance, or incorrect extraction → **Phase 11.2 = FAILED until corrected.**

## No False Verification (mandatory)

Do not declare "real-world forecasting verified" unless the evidence proves the source videos are genuine real-world recordings. Do not treat a synthetic video, a generated fixture, a deterministic test video, or an OpenCV-generated scene as genuine real-world traffic, no matter how realistically it was processed. Do not fabricate evidence, manually edit database values to make a result pass, alter metrics to look better, lower thresholds to achieve readiness, or claim production accuracy from a tiny dataset.
